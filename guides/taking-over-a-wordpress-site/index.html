Taking over a WordPress site someone else built

Any developer who works in WordPress can take over a site someone else built. How smoothly it goes comes down to three things: logins in your business's name, a fresh backup of the files and the database, and a new developer who learns how the site fits together before changing anything. Below: what to hand over, what the first checks should be, the red flags, and when a rebuild is the cheaper path.

By Hashim H., Elimenti. Published November 25, 2026.

Who can take it over

WordPress is open-source software. The firm that built your site doesn't own the platform, so you aren't tied to it. A freelancer, an agency or a small studio like ours can pick the site up, and the site doesn't have to move to do it. It can stay on the same hosting, at the same address, with the same email, while the person looking after it changes.

What varies is how long the new developer needs to learn it. One common theme and a short list of plugins is quick. Custom code, more than one page builder or a long plugin list nobody can explain takes longer. A developer worth hiring will look before quoting, and say which kind of site you have.

What to gather before the handover

Most of these sit with you or your old developer already. Collect them before the new developer starts, so the first hours go to the site instead of to chasing logins.

  • A WordPress user for the new developer. Their own account with the Administrator role, created from Users in the dashboard. Don't hand over your own password; a separate user can be removed later without touching yours.
  • Hosting access. Needed to take backups, see what the server runs and restore the site if an update goes wrong. Some hosts let you invite a second user instead of sharing the main login.
  • The domain registrar and DNS. Not to change them, but so whoever works on the site knows where your email is set up and doesn't break it.
  • Premium licenses. Paid plugins and themes, such as Elementor Pro, a forms plugin or a premium theme, each come with a license. Note which account holds each one and when it renews.
  • Existing backups. Where they're kept, how often they run, and whether anyone has ever restored one.
  • Notes from the old developer. A child theme, custom code snippets, redirects or email routing set up at the host: anything that lives outside the usual WordPress screens.
  • A list of what the site has to do. Every form and the inbox it sends to, booking or payment links, newsletter signups, and anything connected to another system.

If something on that list is in the old developer's name, or nobody can get into it, sort that out first. What to do if your web designer disappears covers getting the domain, hosting and logins back.

Before anything changes: the onboarding pass

A careful takeover starts slowly. Nothing should be updated, edited or deleted until the new developer knows what's there. In order:

1. A fresh backup, kept off the server
Files and database both, since WordPress keeps content in the database and the theme, plugins and uploads in files. A backup stored only on the same server can disappear with it.
2. An inventory of the build
The theme and whether a child theme holds the customizations, every page builder, every plugin with its version and whether it's active, and any custom code.
3. A map of which tool controls which page
ABN Construction Group's site runs two page builders, Elementor and Neuron, plus a slider plugin and an SEO plugin. On a build like that, a careless edit can break a layout on a page nobody was watching, so we learned which tool runs each page before touching any of them.
4. A look at what's waiting
Pending WordPress, theme and plugin updates; plugins whose page on WordPress.org shows no update in a long time; and the server's PHP version compared with WordPress's current requirements.
5. A test of everything that brings in business
A test message through every form, checked at the inbox it should reach. The phone number tapped on a phone. Booking, payment and signup links clicked through to the end.
6. A short write-up for you
One page: what the site runs on, where the backups are, what's out of date and what should happen first. It's the document you'll want if you ever change developers again.

The first updates

Updates are where takeovers go wrong. A site that has sat untouched for a while can have a long queue of them, and running the whole queue at once on the live site is how a layout breaks with nobody sure which update caused it.

  • Back up before every round. WordPress's own guide to updating says to have a backup before you start.
  • Test on a staging copy if your host offers one. Otherwise update one item at a time, at a quiet hour, and check the main pages after each.
  • Give the page builder and the theme the most care. They control the layouts, so they're the updates most likely to change how pages look.
  • Check the license when a premium plugin won't update. A lapsed license, or one sitting in someone else's account, is the usual reason.
  • Keep a log. What was updated, from which version to which, and when. If something looks wrong a week later, the log says where to start.

Red flags

  • The old developer holds the only Administrator login, or the hosting is in their name. Fix that before anything else.
  • Premium licenses are in the old developer's account. You can't renew a license from an account you can't open, and a lapsed one usually means no more updates for that plugin.
  • Nobody knows when the last backup ran, or a backup has never been restored to prove it works.
  • Changes were made to the theme's own files instead of a child theme. The next theme update can wipe them out.
  • Several plugins do the same job: two form plugins, two SEO plugins, two caching plugins. Overlapping plugins are a common source of conflicts.
  • A new developer who runs every update on day one, or proposes a rebuild before looking at the site.

When a rebuild costs less

Keeping the site you have is usually the cheaper choice, until the upkeep starts costing more than it saves. The signs:

  • Small edits regularly break something somewhere else.
  • The theme or a page builder is no longer maintained, so updates stall or damage the layouts.
  • The site is slow or awkward on phones because of what it's built on, not what's on it.
  • Most of what you pay each month goes to keeping the site standing rather than improving it.

Two or more of those, and it's worth pricing a rebuild next to a year of care. Our guide to redesign or refresh has a scorecard you can run yourself, and website redesign covers how a rebuild with us works.

Common questions

Can any WordPress developer take over my site?

Yes. WordPress is open-source, so no firm owns the platform your site runs on, and any developer who works in WordPress can take it on. How smoothly it goes depends on whether the logins are in your business's name, whether there's a current backup and how much custom work the first developer did.

Should I give the new developer my own password?

No. Add them as their own user with the Administrator role, from Users in the WordPress dashboard, and remove that user when the work ends. That way their access can be taken away without changing your login. Do the same at your host if it lets you add another user.

Will my website go down during the handover?

It shouldn't. Changing developers doesn't move the site: it stays on the same hosting and domain, and visitors see no difference. The risky moments are updates and edits, which is why a careful developer backs up first and changes one thing at a time.

How long does it take a new developer to learn an existing site?

It depends on how the site was built. One theme and a few plugins can be learned quickly; several page builders, custom code or a long plugin list take longer. Ask for the onboarding pass to be estimated before it starts, the same as any other task.

Do I need my old developer's permission to switch?

You don't need permission to hire someone else. You need access: the domain, hosting and an Administrator login in your business's name, plus any premium licenses. If those are in the old developer's name, ask for them to be moved to yours, and check your contract for who owns the design and code.
